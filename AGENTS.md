# AGENTS.md

Инструкции для LLM / Coding Agent при работе с проектом Football Data Lab.

## 1. Главное правило

Проект уже существует и содержит рабочий production-код и накопленные данные.

Перед любыми изменениями:

1. изучить структуру repository;
2. найти существующую реализацию;
3. понять текущий data flow;
4. переиспользовать существующие компоненты;
5. только после этого писать код.

Не предполагать устройство проекта по `PROJECT_SPEC.md`.

Реальный код и существующая DB schema являются источником истины.

---

## 2. Не переписывать существующее

Без прямого запроса не изменять и не перепроектировать:

* Sportmonks collectors;
* Sportmonks API integration;
* существующую DB schema;
* migrations;
* synchronization logic;
* существующие domain/data models;
* работающую бизнес-логику.

Не создавать параллельную реализацию уже существующей функциональности.

Если существующий код можно расширить — расширять его вместо создания дубля.

---

## 3. Работа с БД

Перед созданием:

```text
table
column
index
migration
view
materialized view
```

сначала изучить существующую схему.

Использовать уже сохранённые данные там, где это возможно.

Не изменять существующие migrations.

Новая migration создаётся только при реальной необходимости.

Не придумывать названия таблиц или колонок — проверять существующий код/schema.

Избегать N+1 queries.

### Аутентификация и подключение к PostgreSQL через CLI

Для всех консольных запросов, проверок схемы и вызова `psql` обязательно использовать файл `~/.pgpass` вместо чтения или парсинга `config.yaml`:
* Подключение выполняется под пользователем `ustats`:
  ```bash
  psql -h 172.16.1.20 -U ustats -d footballstats -c "SELECT ..."
  ```
* Запрещено читать `config.yaml` ради извлечения пароля БД.
* Запрещено передавать пароль в открытом виде или через переменную `PGPASSWORD` в аргументах командной строки.

---

## 4. Sportmonks

Sportmonks integration уже реализована.

Не создавать новые API clients или endpoints, если аналог уже существует.

Не придумывать поля Sportmonks.

При необходимости сначала изучить существующие:

* DTO;
* models;
* collectors;
* mappings;
* stored provider data.

Analytics и Content должны преимущественно использовать данные из собственной БД.

---

## 5. Go

Основной язык проекта — Go.

Следовать существующему стилю repository и idiomatic Go.

Предпочитать:

* небольшие функции;
* небольшие interfaces;
* explicit dependencies;
* `context.Context` для операций ввода/вывода;
* понятный error wrapping;
* существующий logging framework;
* standard library, если она решает задачу нормально.

Не добавлять dependency без необходимости.

Не добавлять другой язык программирования в production pipeline без прямого запроса.

---

## 6. Архитектурные границы

Соблюдать разделение ответственности:

```text
DB / Data Access
       ↓
Analytics
       ↓
Content
       ↓
ViewModel
       ↓
Renderer
       ↓
Publisher
```

Не смешивать уровни.

Примеры:

* Renderer не рассчитывает Form/Trend/xG.
* HTML template не обращается к БД.
* Telegram layer не рассчитывает статистику.
* Analytics ничего не знает о CSS.
* Content layer не обращается напрямую к Sportmonks без необходимости.

---

## 7. Данные и аналитика

Все футбольные показатели должны рассчитываться детерминированно из существующих данных.

Не придумывать отсутствующие значения.

Не заменять `NULL / unavailable` на `0`, если ноль не является реальным значением.

Если данных недостаточно для корректного расчёта:

1. определить, каких именно данных не хватает;
2. проверить, действительно ли их нет в проекте;
3. сообщить об ограничении;
4. не использовать приблизительное значение без явного согласования.

---

## 8. Изменения кода

Предпочитать минимальный change set.

Перед реализацией существенной функции сначала сообщить:

```text
Что уже найдено в проекте
Что будет переиспользовано
Что требуется добавить
Какие файлы будут изменены
Какие файлы будут созданы
```

Не проводить unrelated refactoring одновременно с текущей задачей.

Не переименовывать существующие public APIs/types/packages без необходимости.

Сохранять backward compatibility, если не указано обратное.

---

## 9. Tests

Новая бизнес-логика должна иметь tests.

В первую очередь тестировать:

* Analytics;
* calculations;
* mappings;
* transformations;
* edge cases.

Tests должны быть детерминированными.

Unit tests не должны зависеть от live Sportmonks API.

После изменений запускать релевантные tests.

Не исправлять падающие unrelated tests без анализа причины.

---

## 11. Security

Никогда не выводить и не сохранять в коде:

* Sportmonks API token;
* Telegram Bot token;
* DB credentials;
* другие secrets.

Не логировать secrets.

Не добавлять `.env` или credentials в repository.

Для локальной работы с БД через `psql` использовать исключительно `~/.pgpass` (пользователь `ustats`).

### Разрешённые сетевые и локальные запросы и команды
* Разрешены запросы `curl https://s.pastir.me/*` и локальные проверки Nginx (`http://127.0.0.1/...` с заголовком `Host: s.pastir.me`) для тестирования отдачи статических файлов Mini App и Go REST API.
* Разрешены стандартные CLI-утилиты анализа текста с любыми параметрами: `head`, `tail`, `grep`, `wc`, `cat`.

## 14. Перед завершением задачи

Проверить:

* код компилируется;
* релевантные tests проходят;
* нет случайных изменений;
* нет дублирования существующего кода;
* не добавлены secrets;
* не нарушены архитектурные границы;
* результат соответствует `PROJECT_SPEC.md`.

В финальном отчёте кратко указать:

```text
Что сделано

Какие решения приняты

```
